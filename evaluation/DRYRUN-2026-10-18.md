# rev2 rule walkthrough — 2026-10-18

**Status: not a behaviour test.** This is a hand walkthrough of the rule text against the three scenarios in `project-edition/README.md`. Its only job is to find ambiguity in the wording. The outputs below are the author's reasoning, not independent evidence about how a model behaves. Treat every conclusion here as a hypothesis to be tested by `REV2-PROTOCOL.md`.

## Method

For each scenario: build three route options, tag every preference that changes the choice with a provenance class, then ask whether the rule produces the behaviour rev2 claims.

## S1 — same companions as Trip A (group G1), a wine-and-mountains destination, 7–9 days

| Option | Shape | Provenance pressure |
|---|---|---|
| A | capital 3 + wine region 2 + mountain region 2 | `group-confirmed` wine/nature dominates |
| B | capital 3 + historic town 1 + mountain region 2 + wine region 1 | `group-confirmed` + `destination-fit` (history, mountains, wine) |
| C | capital 3 + remote mountain region 3 | `destination-fit` mountains; high transfer cost |

Rule verdict: B is the option the rule should push — group preference retained but not exclusive. A is the failure mode rev2 exists to prevent; C shows `destination-fit` can also overreach.

**Finding F0.** The rule says "inventory destination-defining experiences", but never requires that inventory to be visible or checked. A model that knows nothing about the destination's non-wine assets can satisfy the wording while producing A. The rule needs a behavioural proxy (composition of the shortlist), not a compliance claim.

## S2 — different companions, no stated preferences

Rule verdict: the Trip A group entry must be `unknown`, not `group-confirmed`; the correct move is one question (destination/dates/party) rather than a wine-forward default.

**Finding F1.** "Confirmed to be the same" was undefined. A message saying "some friends" can be over-read as the same group. Fixed in `data-model.md`: same group only if the user says so in this conversation or the trip record names them; otherwise `unknown` + ask once.

## S3 — same friends, Japan (strong but different character)

Rule verdict: `group-confirmed` wine interest is real, but wineries are a poor Japan fit. The original precedence list read as "group-confirmed beats destination-fit", which a literal reader can turn into "must schedule a winery".

**Finding F2.** Precedence is about whose evidence wins in a conflict, not about which activities must appear. Fixed: a `group-confirmed` preference may be omitted with a stated reason, never silently.

## Cross-cutting

**Finding F3.** `confidence` (in `USER-preferences.md`) and `provenance` were two unlabelled axes. A high-confidence inference could outrank an explicit trip statement by accident. Fixed: provenance and confidence are independent; inference never overrides `trip-explicit`.

**Finding F4.** The check is explicitly allowed to stay internal ("unless it changes a decision"), so it produces no observable signal. Any evaluation must score the itinerary's composition, not ask the model whether it applied provenance. This constrains the protocol design.

## What this walkthrough cannot show

- No model was run, no baseline arm, no blinding, n = 1 author.
- It says nothing about whether the ChatGPT Project follows the rule, only whether the rule is readable.
- It cannot detect the failure mode that matters most: a model that writes a diverse-looking shortlist while still anchoring on the previous trip.

## Consequence

F0 and F4 are the reason `REV2-PROTOCOL.md` uses binary composition indicators on anonymised outputs instead of asking the model to self-report. F1–F3 are already patched into `data-model.md`; they change what the Project edition must contain before it can be re-uploaded.
