# Pilot run — 2026-10-19 — NOT EVIDENCE

Purpose: test whether the kit in `RUNBOOK.md` produces outputs the indicators can distinguish. One run per cell, same model family for generation and scoring, no independent model. **This cannot support or refute the claim that the provenance rule works.** It can find broken instructions, dead scenarios and unscoreable indicators, and it did.

## Setup

- Arm A: v1.0.0 skill (`git archive v1.0.0`), no provenance rule.
- Arm B: v1.1 workspace edition, provenance rule present.
- Identical synthetic `travel-data/USER-preferences.md` in both arms (G1 group, cross-trip diversity, editorial).
- Six generations: S1/S2/S3 × A/B, one each.
- Process notes stripped before scoring; arm mapping kept out of the raters' view.
- Two blind raters, same prompt, no arm information, quotes required.

## What the pilot actually found

**1. S3 discriminates, and for the intended reason.**
Arm A wrote: *"closest to the formula that already worked … it recycles the 2025 activity mix"* and made a wine-led route its first option for the S3 destination. Arm B had zero wine mentions and led with autumn foliage, onsen and art islands. This is the failure mode rev2 was written for, reproduced in one run.

**2. S1 discriminates, but on a thinner margin than expected.**
Arm A's three options were all wine-and-mountain shapes (*"wine valley + close mountains (best fit)"*). Arm B also led with a wine route, but its option B was *"cave, canyon, monastery, city layers"*, which is what made I1 pass. Both raters scored this identically, but the pass depends on one option in one output; a one-word difference in emphasis would flip it.

**3. S2 is a dead scenario for discrimination.**
Both arms avoided asserting the colleagues' preferences. It remains useful as a guard (a future rule change that leaks group preferences would fail it), but it should not be counted as evidence of improvement.

**4. Every output contained process notes the skill itself asks for.**
Six of six generations appended "Notes for you / Workspace note / No files written" paragraphs, because the skill instructs the model to disclose archival status. These notes name the preference file and the group, which would have identified the arm to a rater. They were stripped before scoring. Product-level consequence: the rule is followed, but it adds meta-commentary to every answer — worth revisiting separately from evaluation.

**5. One run claimed a file write that never happened.**
The S1 arm A output stated it had *"created a new trip ledger at `travel-data/trips/<destination>-2027/` with the four starter templates filled"*. The disk shows no such directory in either arm. The claim was false, and it is exactly the failure the skill's own "claim persistence only after verification" rule exists to prevent. No indicator caught it because none looks at the filesystem. **New indicator I5 added** (see protocol amendment).

**6. I4 held everywhere.**
No invented bookings, prices or confirmed hours. One borderline phrase (*"rural districts shut down after 18:00"*) split the raters' reasoning but not their verdict.

## Consequences for the 18-run experiment

- Keep S1 and S3; keep S2 as a guard only.
- Add **I5 — persistence truthfulness**: if the output claims a file was created or updated, the path must exist and its content must match; check the arm's `travel-data/` before and after each run.
- Strip process notes, and record whether they appeared (secondary observation).
- Use at least two model families for generation if possible; same-family raters inflate κ.
- The pilot's 2/2 directional result is consistent with the claim but is **not** evidence: n = 1 per cell, one model family, raters who share its blind spots.
